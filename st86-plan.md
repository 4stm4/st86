# st86 — стенд для машины «Челябинск-1» (КР1810ВМ86): архитектура, спецификации, план

**Версия документа:** 1.2 (v1.1 + ревизия: адресация, event-order, метрики, FIFO-инварианты, CPU-контракт) · **Статус:** утверждён к реализации · **Код на этом этапе не пишется** — документ является заданием для агентов-исполнителей.

---

## 1. Назначение и роль стенда

Машина — **«Челябинск-1»**, стенд — **st86**. st86 — **не эмулятор, а стенд**: модель платы + прогон сценариев + утверждения + метрики латентности + сверка с железом. Проверочная обвязка — основная часть, не вспомогательная.

Стенд — **автоматический и объективный критерий «работает / не работает»** для собственной ОС (вытесняющая многозадачность, кольца подачи/завершения вместо синхронных syscall, VFS поверх FAT, буферный кэш с отложенной записью). Код ОС пишут ИИ-агенты; всё, что нельзя проверить машинно, для проекта почти бесполезно.

Главный приоритет ОС — **ограниченная худшая задержка** (отсутствие лагов), а не средняя пропускная способность. Стенд обязан измерять именно это, и метрики латентности должны быть доступны как утверждения в тестах.

### Жёсткие требования (неизменяемые)

| № | Требование |
|---|---|
| 1 | **Детерминизм**: один вход → побайтово тот же результат и та же потактовая трасса (в рамках одной версии стенда) |
| 2 | **Headless CLI**: собрать образ → запустить → проверить → код возврата; GUI в основном режиме нет |
| 3 | **Скорость**: доли секунды на тест; бенчмарк-порог ≥ 50 млн эмулируемых тактов/с — CI-тест |
| 4 | **Наблюдаемость**: дамп регистров/памяти, трассировка, снапшоты, «перемотка» через реплей от снапшота |
| 5 | **Инструментовка латентности**: max-интервал с запрещёнными прерываниями, гистограмма «IRQ → пробуждение задачи» — как проверяемые утверждения |
| 6 | **Язык — Rust**, однопоточное детерминированное ядро, никакого wall-clock внутри модели |

### Тулчейн и качество диагностики

- ОС собирается **gcc-ia16**. Следствия для st86: загрузка образов в формате **ia16-elf** и чтение **DWARF** — трассировка и диагностика **символьные** (функция/строка), не в голых адресах. Сырой бинарный формат остаётся для ROM-стабов и самотестов стенда.
- Код ОС целиком пишут ИИ-агенты, владелец проекта код не пишет. Поэтому качество диагностики — **требование, а не удобство**: одна команда запуска, машиночитаемый JSON наряду с человекочитаемым, осмысленные коды возврата, и диагностика, указывающая **что** сломалось (какое утверждение, какой инвариант, где в коде ОС), а не только факт падения. Агент не догадывается по косвенным признакам.

## 2. Моделируемая система («Челябинск-1»)

- ЦП: КР1810ВМ86 (8086), **5 МГц**, реальный режим, 1 МБ, без MMU/защиты. Это **не клон IBM PC**: своя карта портов, своя периферия. Готовые PC-эмуляторы не подходят.
- **20-битное физическое адресование**: `physical_address = ((segment << 4) + offset) & 0xFFFFF`. Адрес `FFFF:0010` → `0x00000` (wraparound; на 8086 нет линии A20 — усечение до 20 бит на уровне BIU маской `& 0xFFFFF`). Обязательный тест M1 (`wraparound_20bit`).
- КР1810ВН59А (≈ i8259): контроллер прерываний, порты `0x20/0x21`.
- КР580ВИ53 (≈ i8253): таймер, порты `0x40–0x43`.
- Регистровый банк консоли/конфигурации: `0xE0–0xE6`, флаги готовности. Реализация на плате — защёлки + буферы; конкретная логика фиксируется схемой ревизии платы.
- `FIFO_FREE` — 16-битный **read-only** входной регистр свободного места видео-FIFO, формируемый отдельной входной защёлкой (не из банка записи). Путь: RP2040 → защёлка → буфер → шина 8086.
- UART: отладочная консоль.
- Блочное устройство: PIO (`rep insb/outsb`), FAT12/16. **DMA нет** (AEN на землю), сектор 512 байт ≈ 1 мс — предсказуемо.
- Видео: отдельная плата на RP2040, принимает поток команд рисования через FIFO на портах в/в. Кадрового буфера в адресном пространстве 8086 **нет**. RP2040 владеет пикселями/поверхностями/кэшем шрифтов, выдаёт VGA, сигналит прерываниями: кадровый синхроимпульс и **нижняя отметка заполнения FIFO** (не «пусто»!). Команды самоограничены (опкод + длина), есть escape-ресинхронизация и запрос возможностей.

### Wait states (параметр по областям, не константа)

| Область | Такты ожидания |
|---|---|
| ОЗУ (AS6C1008, 55 нс) | 0 (READY формируется аппаратно на T2; динамических wait states нет) |
| ПЗУ (класс 28C256, 150–250 нс) | 0 (медленнее → 1) |
| Регистровый банк консоли (защёлки+буферы, конкретика — по ревизии схемы) | 0 |
| ВИ53, ВН59 | 1 (длинные импульсы чтения/записи) + **время восстановления между обращениями** |
| Видео-FIFO | **0 всегда**: IOCHRDY не используется по решению; обратное давление только флагами |

Время восстановления ВИ53/ВН59 моделируется **детектором нарушения** (диагностика/провал теста), а не эмуляцией мусорного чтения: реальное железо здесь молча врёт — стенд обязан кричать.

## 3. Ключевые архитектурные решения (зафиксированы, менять только через ревизию документа)

1. **Одни часы.** `MasterClock: u64` — счётчик тактов ЦП, единственная ось времени. Устройства «ленивые»: состояние вычисляется арифметически от момента чтения (ВИ53 = чистая функция `(t_now − t_load) mod period`). Активные моменты устройств — события в приоритетной очереди `(timestamp, EventId)`.

   **Инвариант: IRQ не является прямым событием исполнения CPU.** Событие устройства только меняет состояние контроллера прерываний (IRR/ISR ВН59). CPU видит INTR исключительно в архитектурно допустимых точках (между инструкциями, между итерациями rep, после снятия тени STI/MOV SS) и выполняет полноценную последовательность INTA. Цепочка: устройство → IRQ → ВН59 обновил IRR/ISR → INTR=1 → CPU в допустимой точке → INTA-циклы → вектор → обработчик. Каждое звено — отдельный шаг с собственным таймингом.

   **Event-order policy** для событий с одинаковым `timestamp`: фиксированный порядок фаз — (1) завершение текущего T-state CPU; (2) обновление состояний устройств (ВИ53 перешёл через 0, FIFO пересёк отметку, VSYNC); (3) публикация IRQ на входы ВН59; (4) проверка INTR/NMI в архитектурной точке CPU; (5) начало следующего T-state. При равенстве `timestamp` внутри одной фазы — строгий лексикографический порядок `(timestamp, device_id, channel_id)`. Никакой зависимости от порядка вставки. Порядок зафиксирован и проверяется тестом.
2. **Устройства с собственной частотой** (RP2040) — через фиксированное рациональное отношение: `t_rp2040 = t_master · num / den`. Параллельности в реализации нет — только события на общей оси. Это и есть ответ на вопрос о детерминизме асинхронной видеокарты.
3. **ЦП в два слоя.** EU (семантика инструкций 8086; набор 8088 SingleStepTests — **оракул семантики**, т.к. EU идентичен, но спецификация и критерий M1 — 8086) и BIU (строго 8086: 16-битная шина, очередь предвыборки 6 байт, T-состояния, wait states — валидируется потактовым набором 8086). Интерфейс: `fetch_byte / read / write` с накоплением тактов. Потактовая точность **обязательна**: без честной предвыборки гистограммы латентности врут на десятки процентов.
4. **Память — горячий путь без диспетчеризации.** Обёрнута в `Memory { data: Box<[u8; 1_048_576]>, rom: BitVec }` (не голый `Box`) — для диагностики (ROM violation, snapshot diff, символьные адреса), но чтение/запись — прямая индексация без хуков. `physical_address` всегда `& 0xFFFFF`. MMIO нет (видео на портах).
5. **Порты — холодный путь**: плоский `match` в `Machine::port_read/write`; устройства — именованные поля `Machine`. Никаких `dyn Device` / `Rc<RefCell<…>>` в диспетчеризации. Трейт `Device` — только внутреннее удобство юнит-тестов.
6. **Состояние = одна serde-структура `Machine`.** Что не в структуре — того не существует. `EventQueue` (с `timestamp`, `event_id`, `event_kind` каждого отложенного события) **является частью `Machine`** — не раннера, не внешнего контекста. Снапшот = полная сериализация (bincode) + copy-on-write диска (грязные блоки + хэш иммутабельного базового образа).
7. **Перемотка назад не реализуется**: периодические снапшоты + реплей от ближайшего. Детерминизм делает это бесплатным.
8. **Метрики латентности — часть ядра**, всегда включены на аппаратном уровне (трекер IF, IRQ→INTA). Программный уровень (IRQ→пробуждение задачи) — через **тестовый порт** (semihosting), см. §5.
9. **Формат MOO** для SingleStepTests (готовый крейт; запасной вариант — свой парсер, формат прост).
10. **Межверсионная стабильность — инвариант атрибуции, не значений.** Трассы версионно-зависимы. Значения метрик меняться могут; инвариант — **«значения не меняются молча»**: любой сдвиг метрики атрибутируется ровно одной причиной — изменился код ОС *либо* изменилась модель. Смешение двух причин в одном изменении запрещено. Операционные правила: (а) обновление эталонов — всегда отдельный коммит, никогда вместе с правкой ОС; (б) при исправлении модели новый эталон снимается прогоном **неизменного** кода ОС под новой моделью — дельта эталона тогда есть чистый вклад исправления модели; (в) CI проверяет механически: коммит, меняющий версию модели или эталоны, не должен менять исходники ОС (сверка по хэшу). Версия модели + хэши конфигураций (wait states, таблица стоимости видеокоманд) — в заголовке каждого артефакта.
11. **Стенд строже железа.** Нарушения протоколов (время восстановления, дисциплина резервирования FIFO) — громкая диагностика, а не воспроизведение последствий. На плату приходит уже вычищенный код.
13. **Снапшот-roundtrip — фундаментальный инвариант ядра**: `run(A→C) ≡ snapshot+restore(B)` — побайтовое совпадение `Machine` (включая `EventQueue`), потока событий и `MasterClock`. Красный = мерж-блокер начиная с M5.
14. **Эталонных метрик мало.** Каждая метрика под процессом атрибуции стоит ручного внимания при каждой правке модели, поэтому канонический набор — **две-три**: `max_irq_blocked`, `irq_to_wake_max`, простой видео-потребителя. Три яруса стоимости: (а) *эталонные значения* — канонический короткий список, полный процесс из решения №10; (б) *пороговые утверждения в сценариях* — неравенства с запасом, их может быть много, правки модели они в норме переживают без внимания; (в) *гистограммы в отчёте* — бесплатны, только для чтения человеком, эталонов не имеют. Добавление метрики в ярус (а) — ревизия этого документа, не рядовой коммит.
15. **Wall-clock допускается только во внешнем benchmark harness.** Результат `Machine` никогда не зависит от wall-clock; бенчмарк M2.6 измеряет реальное время *снаружи* core.

## 4. Модель видеоподсистемы

### 4.1 Уровни (переключаются флагом; L0+L1 — один обязательный уровень)

- **L0 — протокольный валидатор** (стоимость ≈ 0, всегда): разбор команд, рамки (длина, неизвестные опкоды), escape-ресинхронизация, запрос возможностей, **хэш командного потока** (= SHA-256 от сырых байтов, принятых FIFO; отдельно — `command_count`, `opcode_histogram`), счётчики — включая **простой потребителя** (такты RP2040, проведённые с пустой очередью; счётчик есть, прерывания «очередь пуста» **нет**).
- **L1 — модель ресурсов** (дёшев, всегда): поверхности и их жизненный цикл, кэш шрифтов как метаданные; детектор «рисование в освобождённую поверхность».
- **L2 — растеризатор → PNG** (golden-тесты, вне CI-дефолта, веха M9).

Пиксельная корректность **не влияет** на состояние 8086 (ОС пиксели не читает) — единственное видимое: состояние FIFO и два прерывания. Эмуляция ARM-ядра RP2040 — исключена.

### 4.2 Модель времени FIFO (обязательна на всех уровнях)

- Глубина **8 КБ**, побайтовый учёт занятости.
- Темп потребления — **таблица стоимости по опкодам** (файл конфигурации; хэш в артефакты; калибруется на HIL микробенчмарками; прошивка RP2040 обязана выдерживать бюджет — «железо соответствует модели», не наоборот).
- **Две отметки**: верхняя — ОС прекращает запись и блокирует задачу; нижняя (≈ ¼) — прерывание на дозаполнение. Канонический тест — конвейер без пузырей.
- Прерывания vsync и нижней отметки — события в общей очереди, приходят в предсказуемые такты. Прерывания «очередь пуста» не существует: ожидание полного опустошения пузырит конвейер (решение платы, не параметр).

### 4.3 Дисциплина «сначала резервируй, потом пиши»

Переполнение FIFO **невозможно по построению**: программа проверяет не «полон ли FIFO», а «есть ли место под N байт» (N — длина всей команды), затем пишет команду целиком `rep outsb` без проверок. Команда никогда не рвётся посередине.

- Регистр `FIFO_FREE` (§2) отдаёт **16-битный счётчик свободного места** (`in ax, dx` — атомарное чтение одним шинным циклом; торн-рид исключён выбором ширины).
- Семантика счётчика — **консервативный снимок**. Формальный инвариант: `0 ≤ reported_free ≤ actual_free ≤ FIFO_CAPACITY`. Нарушение — дефект модели, не допустимое поведение.

   **Алгоритм в sim** (гонок нет — однопоточность, одни часы): модель ведёт `fifo_used: u16`. При записи команды в FIFO: `fifo_used += cmd_len`. При созревании события потребления (ленивый пересчёт от `MasterClock` по таблице стоимости): `fifo_used -= consumed`. Порт `FIFO_FREE` при чтении возвращает `FIFO_CAPACITY - fifo_used`, вычисленное **в T-state чтения порта**, без дополнительных задержек. Между чтением и использованием значения в ОС время идёт только вперёд → инвариант `reported ≤ actual` выполняется автоматически. (Заметка для агентов: если добавить wait state на чтение этого порта, значение должно вычисляться *после* wait state, в момент защёлкивания данных на шину.) Поскольку между чтением порта и записью команды RP2040 может только вычерпать ещё (время идёт вперёд) — инвариант `reported_free ≤ actual_free` выполняется автоматически.
- Железо защёлкивает **залипающий бит переполнения** (один триггер); в корректной работе он не взводится никогда.
- **Детектор в стенде**: модель помнит последнее прочитанное ОС значение счётчика, списывает с него длины записанных команд; уход в минус = диагностика, даже если физически место было. Ловим нарушение дисциплины, а не последствие.
- **Режим внесения неисправностей** (секция `[fault]` сценария): в заданный такт **искусственно** взводится залипающий бит аппаратной неисправности (физического переполнения при корректном драйвере не происходит), поток помечается рассинхронизированным, приёмник игнорирует всё до escape-последовательности. Только так тестируется код восстановления, который иначе мёртв навсегда.

### 4.4 Спецификация протокола — отдельный артефакт, две реализации

Модель видеокарты в st86 и прошивка RP2040 — **две независимые реализации одной спецификации протокола**. Спецификация (опкоды, длины, escape, запрос возможностей, семантика счётчика свободного места и отметок) — отдельный версионируемый документ, а не «то, что делает код». Сверка двух реализаций на общих трассах команд — самостоятельная ценность (веха M8.6).

Границы по приоритету: **L0 закрывает планировщик, память, ФС, системные вызовы и весь бюджет латентности без единого пикселя.** Пиксели нужны только при отладке графического драйвера. Прошивка RP2040 пишется позже, параллельно драйверу, и **на критическом пути не стоит**.

## 5. Спецификация: тестовый порт (semihosting) `0xF0–0xF6`

Центральная точка системы: через него — маркеры ОС, утверждения сценариев, корреляция латентности, сверка с железом. **Правило двойного стандарта**: каждая возможность тестового порта обязана иметь реализацию на реальной плате (через отдельную защёлку на тех же адресах `0xF0–0xF6`, читаемую служебным RP2040) — исключения перечислимы и помечены `backends = ["sim"]`.

| Порт | Направление | Назначение |
|---|---|---|
| `0xF0` | out | Код операции маркера (см. ниже) |
| `0xF1` | out | Аргумент, младший байт |
| `0xF2` | out | Аргумент, старший байт |
| `0xF3` | out | Фиксация: запись сюда атомарно публикует маркер (опкод+аргумент) с таймстемпом `MasterClock` |
| `0xF4` | out | Управление: `0x01` = завершить тест, код возврата в аргументе; `0x02` = запросить снапшот |
| `0xF5` | in | Присутствие стенда: читается `0xC1` в симе, на железе — открытая шина. ОС в тестовой сборке может ветвиться, в релизной сборке порт не трогается |
| `0xF6` | — | Резерв |

**Опкоды маркеров** (расширяемый список, tagged): `0x01` чекпоинт (аргумент = ID чекпоинта), `0x02` планировщик выбрал задачу N, `0x03` задача N проснулась, `0x04` начало измеряемой секции, `0x05` конец секции, `0x10–0x1F` пользовательские.

Каждый опубликованный маркер попадает в **поток событий** (канал трассировки №1, всегда включён) с таймстемпом. Гистограмма «IRQ → пробуждение» = корреляция фронта IRQ на входе ВН59 с ближайшим последующим маркером `0x03` того же контекста.

## 6. Спецификация: формат сценария v1 (TOML)

```toml
version = 1                     # версия формата, обязательна
image = "build/os.elf"          # ia16-elf (gcc-ia16); сырой .bin допустим для ROM-стабов
disk  = "images/fat16-base.img" # опционально
cycle_limit = 50_000_000        # предохранитель от зависаний
backends = ["sim", "hil"]       # по умолчанию оба; адреса тестового порта одинаковы; sim-only — явно и с обоснованием в комментарии

[config]
wait_states = "boards/rev1.ws.toml"     # таблица по областям, хэш идёт в отчёт
video_cost  = "boards/rev1.vcost.toml"  # таблица стоимости опкодов

[[assert]]
kind = "checkpoint_order"
values = ["boot", "vfs_ready", "done"]

[[assert]]
kind = "metric"
name = "max_irq_blocked"    # от CLI до момента, когда прерывание могло бы быть принято
max_cycles = 500

[[assert]]
kind = "metric"
name = "irq_to_wake_max"    # максимальная наблюдённая задержка (абс. max, не перцентиль)
irq = 0
max_cycles = 2000

[[assert]]
kind = "mem"
addr = "0x05010"           # всегда физический (линейный) адрес, не seg:off
equals_hex = "DEADBEEF"

[[assert]]
kind = "uart_contains"
text = "OK"

[[assert]]
kind = "video_stream_hash"   # L0; хэш = SHA-256(raw FIFO bytes)
equals = "sha256:..."
# при несовпадении отчёт: first_difference_offset, expected/actual byte,
# decoded_command_index, opcode — агент видит *что* разошлось

# режим неисправностей (опционально)
[fault]
kind = "fifo_overflow_flag"  # инъекция аппаратной неисправности, не физическое переполнение
at_cycle = 12_000_000        # или at_command = N
```

Правила:
- Утверждение — предикат над (финальное состояние + метрики + поток событий). Выход раннера: код 0/≠0 + машиночитаемый JSON-отчёт с версией модели и хэшами конфигураций.
- Пороги латентности — **в тактах**, не в микросекундах (частота не протекает в утверждения; на HIL пересчёт по частоте с допусками).
- **Неравенства с запасом** — в сценариях; **точные значения** — только в эталонных файлах, обновляемых осознанно (см. решение №10).
- Коды возврата раннера `st86`: `0` — успех; `1` — провал утверждения; `2` — нарушение инварианта/дисциплины (сработал детектор); `3` — исчерпан `cycle_limit`; `4` — внутренняя ошибка стенда. JSON-отчёт пишется во всех исходах, включая `4`.
- Формат версионируется с первого дня; утверждения — расширяемый tagged enum.

## 7. Трассировка: три канала

| Канал | Что | Стоимость | Режим |
|---|---|---|---|
| 1. Поток событий | IRQ, порты, маркеры тестового порта, снапшот-точки | копеечная | всегда включён (это вход утверждений) |
| 2. Инструкционная трасса | адрес, опкод, дельта тактов, регистры по маске изменений; бинарный компактный формат, кольцевой буфер | средняя | по умолчанию выключена |
| 3. Потактовая шина | T-состояния, циклы | высокая | только отладка стенда / сверка SingleStepTests |

**Стратегия против гигабайтов — детерминизм, а не фильтры**: обычный прогон без трассы; упал → раннер автоматически перезапускает тот же сценарий от ближайшего снапшота с трассой, включённой на последних N миллионах тактов. Трасса — инструмент второго прогона, а не налог на каждый. Заголовок трассы: версия модели + хэши конфигураций (старые эталоны не сравниваются с новой моделью незаметно).

## 8. HIL (hardware-in-the-loop)

Потактовая сверка с железом невозможна и не нужна. Сверка — **на уровне наблюдаемого состояния**, формально отделённого от sim-only:

| | Стенд (sim) | Железо (HIL) |
|---|---|---|
| Точные такты, `MasterClock` | да | нет (пересчёт в физ. единицы с допуском) |
| Поток событий тестового порта | да | да (служебный RP2040 читает защёлку `0xF0–0xF6`, ставит метки 133 МГц, стримит по USB) |
| Порядок чекпоинтов | да | да |
| Контрольные суммы областей памяти | да | да (ОС считает и отдаёт через тестовый порт) |
| Внутреннее состояние `Machine` | да | нет |
| UART-поток | да | да |
| Метрики латентности | в тактах | в физ. единицах, с допуском |

Отношение эквивалентности sim↔HIL определено на пересечении: потоки событий совпадают, контрольные суммы равны, метрики в допусках.

**Источник метрик на HIL — служебный RP2040**, не сама ОС и не ВИ53. Разрешение 133 МГц (~7,5 нс) на два порядка лучше ВИ53 (~0,84 мкс), возмущение минимально: 8086 делает один `out` (~2 мкс, детерминированно), RP2040 ставит метку. UART для маркеров **не используется**: байт при 115200 ≈ 87 мкс — сопоставимо со всем бюджетом на запрещённые прерывания, и контенция с отладочной консолью. Тестовый порт на плате — те же адреса `0xF0–0xF6`, что в sim → один код ОС, одни сценарии, никакой условной компиляции.

- Раннер один, бэкенда два: `--backend=sim | --backend=hil:usb` (служебный RP2040 по USB) (на железе — тайм-ауты вместо лимита тактов).
- Ни одно утверждение основного набора не опирается на состояние, невидимое с платы. Sim-only-утверждения (например, негативный тест дисциплины резервирования — железо нарушение переживёт молча/недетерминированно) — явный атрибут `backends = ["sim"]`, список исключений перечислим и ревизуется в M8.
- Калибровка на плате: микробенчмарки «N одинаковых видеокоманд» → таблица стоимости; сверка wait states со схемой. Прошивка RP2040 несёт **бюджет стоимости на команду** как контракт — железо обязано соответствовать модели.

## 9. План по вехам с подзадачами

Оценки: S — дни, M — неделя, L — больше недели (один исполнитель). Каждая веха закрывается зелёным CI-критерием.

### M0. Фундамент репозитория (S)
- **M0.1** Workspace: крейты `core` (машина), `runner` (CLI), `formats` (сценарии/трассы/снапшоты). Границы крейтов = границы будущих API.
- **M0.2** Разведка крейта MOO: скачать оба набора SingleStepTests, распарсить целиком, замерить. Выход — решение «крейт годен / пишем свой парсер» с цифрами. Единственная разведочная подзадача плана.
- **M0.3** Версионирование: константа версии модели; заголовок (версия + хэши конфигураций) во всех артефактах; CI-правила атрибуции (решение №10: смена версии/эталонов не смешивается с правкой ОС, сверка по хэшу исходников) — заглушкой до M4.
- **M0.5** Reference CPU contract: до M1 зафиксировать в документе поведение 8086 по точкам разночтений: reset state, `physical_address & 0xFFFFF`, неопределённые/зарезервированные флаги, INTR/NMI, INTA, очередь предвыборки, segment override, LOCK, REP, тень STI/MOV SS. Источники: Intel iAPX 86 User's Manual + SingleStepTests. Цена — дни; отдача — агенты не трактуют архитектуру по-разному.
- **M0.4** Разведка ia16-elf/DWARF: собрать gcc-ia16 «hello», распарсить ELF и отладочную информацию (`object` + `gimli`), проверить отображение seg:off → символ/строка. **Основной CI-путь**: `ld --print-map` + `nm` + привязка к базам сегментов (работает в 100% случаев для real mode). **DWARF — nice-to-have** для L2-отладки: поддержка 16-битных указателей в gimli исторически кривая, gcc-ia16 может генерировать нестандартные DIE. Выход — решение «какой парсер для CI, пригоден ли DWARF для отладки».
- **Критерий:** оба набора парсятся; разведка ia16-elf дала решение; Reference CPU contract в репозитории; CI собирает workspace; версия проставляется в пустой отчёт.

### M1. Семантика ЦП (L)
- **M1.1** Типы состояния: регистры/флаги/`Cpu` — plain-структуры под serde с первого дня.
- **M1.2** Декодер: modrm, префиксы (сегментные, rep, lock), таблица инструкций; тесты декодера до подключения исполнения.
- **M1.3** Исполнение по группам, каждая гоняется по подмножеству набора 8088 сразу: (а) пересылки/стек, (б) АЛУ/флаги, (в) переходы/call/ret/int, (г) строковые с rep, (д) mul/div и корявые флаги, (е) BCD. **Из набора 8088 используется только семантика** (АЛУ, флаги, логика переходов, состояние памяти). Потактовые тайминги, размер очереди (4 байта у 8088 vs 6 у 8086) и логика шинных циклов (8-битная шина vs 16-битная) в 8088-тестах **игнорируются** — они переопределяются по даташиту 8086 в M2.
- **M1.4** Прерывания: INT n/INTO/IRET, точки опроса INTR/NMI, прерываемость rep между итерациями, тень STI/MOV SS. **Тень — свойство границы инструкций, не тактов**: после STI или MOV SS прерывания запрещены ровно на одну следующую инструкцию, независимо от её длительности (даже если это длинный `rep movsb`). Реализация «запрет на N тактов» — ошибка.
- **M1.5** Грубый тайминг по справочнику — помеченная заглушка до M2.
- **Критерий:** 100 % инструкционного набора 8086 (семантика/флаги/память); набор 8088 SingleStepTests — оракул, где применим; тест `wraparound_20bit` зелёный; весь набор — единицы секунд.

### M2. Потактовый BIU (L, самая рискованная веха)
- **M2.1** Очередь предвыборки: 6 байт, заполнение/сброс на переходах, интерфейс `fetch/read/write` к EU.
- **M2.2** T-состояния, нечётный адрес слова = два цикла, потактовый счётчик = единственные часы.
- **M2.3** Таблица wait states по областям: быстрый путь памяти без таблицы (битовая карта), таблица — на портах/медленных областях; формат в конфигурации сценария, хэш в артефакты.
- **M2.4** Детектор времени восстановления ВИ53/ВН59: нарушение паузы = громкая диагностика.
- **M2.5** Прогон потактового набора 8086, итеративная доводка (EA, строковые, реакция очереди — основной запас времени вехи). Рекомендуемая техника: генератор случайных валидных последовательностей с рандомизированными wait states и прерываниями на границах → сверка состояния регистров/памяти с семантическим оракулом (EU без таймингов) после каждой инструкции.
- **M2.6** Бенчмарк ≥ 50 млн тактов/с как CI-тест; wall-clock — только внешний harness, результат `Machine` от него не зависит (решение №15).
- **Критерий:** 100 % потактового набора 8086; бенчмарк взят; юнит-тест «два обращения к ВИ53 без паузы» даёт детерминированную диагностику.

### M3. Машина, периферия, раннер (M)
- **M3.1** `Machine`: 1 МБ + битовая карта ПЗУ, плоский `match` портов, `EventQueue`, ленивые устройства.
- **M3.2** ВН59: приоритеты, маски, EOI-режимы, spurious IRQ7, ребро/уровень; юнит-тесты по даташиту отдельно от ЦП.
- **M3.3** ВИ53: режимы 0–5 как арифметика от загрузки, защёлки чтения, события нуля в очереди.
- **M3.4** UART: честные по времени флаги готовности, сток в файл/stdout.
- **M3.5** Регистровый банк `0xE0–0xE6` по спецификации платы.
- **M3.6** Тестовый порт `0xF0–0xF6` по §5; протокол — отдельный документ (контракт с ОС и железом).
- **M3.7** Раннер (CLI `st86`): сценарий v1 (§6), загрузка ia16-elf и сырого bin, лимит тактов, коды возврата по §6, JSON-отчёт; утверждения v1: чекпоинты, память, UART.
- **M3.8** Атрибут `backends` — с первого дня формата.
- **M3.9** Символизация: чтение DWARF из ia16-elf (по решению M0.4), отображение seg:off → символ/строка. Используется всей диагностикой, а также M4.1 и M5.4.
- **Критерий:** headless ROM-тест «ВИ53 → прерывание через ВН59 → UART → маркер завершения» зелёный в CI.

### M4. Метрики латентности (M) — после неё стенд пригоден для агентов
- **M4.1** Два трекера: `max_if_masked` (IF=0 → IF=1, включая тень STI) и `max_irq_blocked` (до момента, когда прерывание могло бы быть принято — тень + INTA-латентность). Каноническая эталонная метрика — `max_irq_blocked`. Топ-N интервалов с адресами и символами (DWARF).
- **M4.2** Гистограмма «фронт IRQ → INTA» (аппаратный уровень, без кооперации ОС).
- **M4.3** Гистограмма «фронт IRQ → маркер 0x03» (программный уровень, тестовый порт).
- **M4.4** Утверждение о худшей задержке внутри `rep insb` передачи сектора (прерываемость длинных rep).
- **M4.5** Утверждения по метрикам: неравенства в тактах; канонический набор эталонных метрик (решение №14) + команда `st86 rebaseline` — перегенерация эталонов прогоном неизменной ОС под текущей моделью; наполнение CI-правил атрибуции из M0.3.
- **M4.6** Негативный самотест: длинная CLI-секция падает по `max_irq_blocked` — «тест умеет падать».
- **Критерий:** M4.6 красный как положено; эталонный сценарий зелёный; гистограммы в JSON-отчёте.

### M5. Снапшоты и воспроизведение (S–M, параллелится с M3–M4)
- **M5.1** Сериализация `Machine`: CPU/EventQueue/Device states через bincode; RAM — **сырым блоком** (`write_all` 1 МБ, не поэлементно; копирование в памяти — микросекунды); EventQueue — компактна (только отложенные будущие события, десятки записей; не история), сериализуется как фиксированная структура сырым блоком (`write_all`), не через serde поэлементно; диск — copy-on-write: грязные блоки + хэш базового образа.
- **M5.2** **Фундаментальный инвариант** (решение №13): `run(A→C) ≡ snapshot+restore(B)` — побайтовое совпадение `Machine` (включая `EventQueue`), потока событий и `MasterClock`; в CI постоянно. Красный = мерж-блокер.
- **M5.3** Периодические снапшоты по интервалу тактов; «перемотка» = рестарт от ближайшего.
- **M5.4** Режим «упал → авто-перепрогон с трассой последних N тактов от снапшота»; хранение трассы — в адресах, вывод — символизированный (M3.9).
- **Критерий:** M5.2 зелёный; демонстрация цикла на искусственном баге.

### M6. Видео: L0/L1 + время FIFO (M; пререквизит — черновой список опкодов протокола)
- **M6.1** Модель времени FIFO: побайтовая занятость, рациональный пересчёт частоты, таблица стоимости (файл, хэш), две отметки, события в очереди.
- **M6.2** 16-битный счётчик свободного места, инвариант консервативного снимка.
- **M6.3** Детектор дисциплины резервирования (списание с последнего прочитанного значения; минус = диагностика).
- **M6.4** L0: разбор, рамки, escape, запрос возможностей, хэш потока, счётчики (включая простой потребителя).
- **M6.5** L1: поверхности, кэш шрифтов, детектор использования освобождённой поверхности.
- **M6.6** Режим неисправностей `[fault]`: инъекция `fifo_overflow_flag` (аппаратная неисправность), залипающий бит, отказ приёмника до escape.
- **Критерий (трёхчастный):** конвейер на двух отметках без пузырей (простой потребителя в допуске); негативный тест дисциплины падает с диагностикой (sim-only); тест восстановления с инъекцией зелёный, включая метрику времени обнаружения бита.

### M7. Блочное устройство и образы (S–M, независим от M5/M6)
- **M7.1** Модель устройства: регистры по спецификации, параметрические задержки готовности, PIO.
- **M7.2** Хост-инструмент сборки FAT12/16 из каталога; **детерминированная укладка**: порядок файлов фиксирован (лексикографический), таймстемпы FAT фиксированы константой (не из ФС хоста) — иначе хэши образов гуляют между сборками.
- **M7.3** Утверждения по диску: контрольные суммы файлов/областей после прогона.
- **Критерий:** «собрать образ → ОС читает файл → сверяет сумму → маркер» зелёный; повторная сборка даёт побайтово тот же образ.

### M8. HIL (M; календарно зависит от платы; M8.1 — как только оживёт служебный RP2040 по USB)
- **M8.1** Бэкенд `hil`: тот же раннер; служебный RP2040 читает защёлку тестового порта `0xF0–0xF6`, ставит метки времени (133 МГц), стримит на хост по USB; хост-раннер принимает поток и строит метрики. Тайм-ауты вместо `cycle_limit`.
- **M8.2** Сверка потоков событий и инвариантов; метрики в допусках.
- **M8.3** Калибровка таблицы стоимости микробенчмарками; сверка wait states со схемой.
- **M8.4** Контракт прошивки RP2040: бюджет на команду, проверяемый на плате.
- **M8.5** Ревизия sim-only-утверждений: перечислимый список, каждое с обоснованием.
- **M8.6** Кросс-сверка реализаций протокола: одна и та же трасса команд подаётся модели st86 и прошивке RP2040 (на плате или в её собственном тестовом контуре), сравниваются счётчики, состояние ресурсов и — при наличии L2 — кадры. Самостоятельная ценность вне HIL-прогонов ОС; календарно не блокирует ничего (прошивка вне критического пути).
- **Критерий:** сценарий из M3 зелёный на обоих бэкендах; отчёт сверки без расхождений вне допусков.

### M9. Видео L2 (M, низкий приоритет, вне CI-дефолта)
- **M9.1** Растеризатор по таблице опкодов, PNG на vsync/по запросу.
- **M9.2** Golden-сравнение с допуском 0 (детерминизм позволяет) + визуальный diff для человека.
- **Критерий:** эталонный рендер-сценарий даёт побайтово стабильный PNG между прогонами.

### Зависимости
Критический путь: **M0 → M1 → M2 → M3 → M4** (после M4 агенты пишут ОС). M5 ∥ M3–M4. M6 и M7 независимы, оба после M3. M8 — дымовой прогон после M3, полная сверка после M6/M7. M9 — после M6. Худший кандидат на делегирование агенту — M2 (итеративная доводка по векторам); лучшие — M5 и M7 (чёткие контракты, богатые критерии).

## 10. Правила для агентов-исполнителей

### 10.1 Инварианты, которые нельзя нарушать
1. **Никакого wall-clock, потоков и источников недетерминизма** в `core`. Крейт `core` — **`#![no_std]` + `extern crate alloc`**: это физически запрещает `std::collections::HashMap` на этапе компиляции, никакой линт не нужен. Разрешены: `Vec`, `Box`, фиксированные массивы, `BTreeMap`/`BTreeSet`, `SmallVec`. Любой PRNG — только сидированный, сид в `Machine`.
2. **Всё состояние — внутри `Machine`.** **Включая `EventQueue`.** Добавил устройству поле — оно обязано попасть в serde-сериализацию. Инвариант M5.2 (решение №13) — арбитр: красный = мерж-блокер.
3. **Память не получает диспетчеризации.** Любое предложение «а давайте повесим хук на чтение памяти» отклоняется — есть каналы трассировки и события.
4. **Стенд строже железа**: нарушения протоколов — диагностика с падением теста, не эмуляция последствий (кроме явного режима `[fault]`).
5. **Точность BIU не разменивается на скорость.** Если бенчмарк M2.6 не взят — оптимизировать интерпретатор, а не резать модель.
6. **Правило двойного стандарта тестового порта**: новая возможность порта без пути реализации на железе не добавляется; sim-only — только с атрибутом и обоснованием.

### 10.2 Как писать тесты и утверждения
- Пороги латентности — в тактах, неравенствами с запасом. Точные равенства — только в эталонных файлах.
- Каждый детектор/метрика сопровождается **негативным самотестом** («тест умеет падать») — по образцу M4.6 и M6.
- Инвариант атрибуции (решение №10): сдвиг метрики имеет ровно одну причину — ОС или модель. Обновление эталонов — всегда отдельный коммит, **никогда** в одном изменении с правкой ОС; при правке модели эталоны перегенерируются `st86 rebaseline` на неизменной ОС. CI это проверяет — не обходить.
- Эталонных метрик две-три (решение №14). Новая метрика по умолчанию идёт в пороговые утверждения или в отчёт; продвижение в эталонный ярус — только через ревизию документа.
- Новый вид утверждения — новый вариант tagged enum + бамп минорной версии формата сценария; старые сценарии обязаны парситься.

### 10.3 Диагностика — требование, не удобство
- Одна команда запуска. Вывод — JSON и человекочитаемый одновременно, во всех исходах.
- Коды возврата различают классы отказов (см. §6). Класс `2` (детекторы) обязан включать: имя инварианта, ожидаемое/фактическое, такт, seg:off и символ/строку кода ОС.
- Сообщение о провале утверждения называет утверждение, ожидаемое и фактическое значение, и для метрик — ссылку на гистограмму в отчёте. «Тест упал» без «что именно сломалось» — дефект стенда, оформляется как баг.

### 10.4 Определение готовности вехи
Веха закрыта, когда: её CI-критерий зелёный; негативные самотесты красные как положено; тест M5.2 зелёный (начиная с M5); бенчмарк M2.6 зелёный (начиная с M2); документация форматов обновлена, если формат менялся.
